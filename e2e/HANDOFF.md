# e2e hand-off: what is not automated here

`e2e/` automates, against real local processes, the 13 §5 scenarios S-01,
S-03, S-04, S-05, S-06, S-07, S-08, S-09, S-12, S-13, S-14, S-15, S-16, S-17,
S-24, S-25, S-32 and S-33, plus T8-03, T17-14, T17-15, T21-13 and T21-14 (see
`README.md`). This file lists every other release-gating scenario of 13 §5 and
every non-functional test of 13 §6 with the reason it is not automated here,
where it is covered at a lower level today, and who owns closing the gap.

Owners: **api** = apps/api maintainers (leaf-2.x), **cli** = apps/jobs-cli
(leaf-4.x), **ops** = CI / staging (leaf-5.3 and the owner), **owner** = needs
the project owner (accounts, money, legal).

## 13 §6 non-functional tests not automated here

| Area | Target | Why not here | Covered at a lower level | Owner |
|---|---|---|---|---|
| Sync batch throughput | `postings:batch` of 100 items ≤ 1.5 s p95, ≤ 600 D1 rows written | Latency targets need a staging Worker (real D1) with a seeded 200k-posting DB; `wrangler dev` timings on a laptop are not representative. | Functional batch limits: `apps/api/src/jobs/routes/discovery/inbox.test.ts` "TD-BULK track 200 ids in one call within D1 limits"; postings:batch tests in `routes/discovery` | ops (staging load script) |
| D1 query budget per request | ≤ 50 queries per request on hot paths | The spec's method is a test helper that counts `prepare()` calls per route inside the api suite; no such counter exists yet (only query-plan checks such as `repo/applications/board.test.ts`). Outside the Worker the count is not observable precisely (wrangler's local trace store records one span per `batch()`). | Not covered | api (add the counter to `test/fakes.ts` and assert per hot route) |
| Board latency | `GET /board` ≤ 300 ms p95 for 500 applications | Load script against staging (real D1 latency). | Query shape: `repo/applications/board.test.ts` (one range scan, indexed sub-queries) | ops |
| Claim contention | 20 devices × 1 poll/s, 100 tasks → no double claims, ≤ 200 ms p95 | The latency half needs staging. Note the target conflicts with the per-device rate limit (`task-poll` 30/min, 05 §1.9): 1 poll/s/device is throttled with 429 — the load script must use ≤ 0.5 poll/s or the rate limit must be raised for it. Exactly-once under real contention is automated here (T21-13: 3 workers, 20 tasks, distinct claims). | `apps/api/src/jobs/routes/automation/claim.test.ts` — "T21-01 50 concurrent claims for 10 queued tasks yield 10 distinct winners" | ops, api (rate-limit note) |
| Change feed | 10k changes → ≤ 20 pages; `410 cursor_expired` → full resync | Server paging + CLI resync are each tested in their suites; 10k rows through `wrangler dev` add only runtime. | `apps/api/src/jobs/routes/sync/changes.test.ts` — "TS-CURSOR-EXPIRED …" (410 and snapshot resume); `apps/jobs-cli/tests/sync/test_puller.py` — `test_410_cursor_expired_triggers_a_snapshot` | api, cli |
| Cost guardrails | Per-user AI budget stops spending at the cap; queue retries never double-charge | Needs a provider that counts calls; the fake provider in `wrangler dev` is free. | `apps/api/src/jobs/queue/handlers/score-postings.test.ts` — "T7-07 a redelivered message neither writes a second row nor counts the budget twice", "T7-09 the daily sub-cap applies too, and a nearly spent budget is never overdrawn" | api |
| CLI resources | 3 API sources × 500 postings ≤ 60 s, ≤ 400 MB RSS | A pytest benchmark of the CLI process alone (the browser excluded); belongs to the CLI's benchmark marker and the per-OS CI matrix. | Not covered | cli |
| Agent bounds | ≤ 60 actions, ≤ 25 AI calls, ≤ 15 min per attempt | Agent-only budget logic with an infinite fixture form. | `apps/jobs-cli/tests/agent/test_agent_units.py` — `test_T19_BUDGET_actions_ai_and_wall_clock`, `test_T19_BUDGET_policy_pause_or_stop` | cli |
